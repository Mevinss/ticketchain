Создай полностью работающий frontend учебного dApp TicketChain —
платформы продажи билетов на мероприятия.

По пользовательскому сценарию ориентируйся на билетный сервис:
каталог → событие → выбор места → покупка → мои билеты → проверка.
Создай собственное оформление, не копируй логотип и бренд Ticketon.

СТЕК

- React + TypeScript + Vite.
- ethers.js v6.
- React Router.
- Адаптивный интерфейс.
- Локализация: казахский и русский.
- Генерация QR и чтение QR камерой.
- Стили: Tailwind CSS либо единая аккуратная CSS-система.
- Зафиксировать версии зависимостей и приложить lockfile.

ИСТОЧНИК КОНТРАКТНОГО API

Я предоставляю TicketChain.sol и фактический ABI.
Они являются источником истины.
Сначала изучи их и составь таблицу:
действие пользователя → функция → аргументы → value → результат.

Не придумывай функции контракта и не изменяй ABI вручную.
Если адрес или ABI отсутствуют, покажи честное состояние
«Контракт не настроен» и инструкцию настройки.
Не изображай успешную покупку без транзакции.

Используемые методы контракта:
admin, eventCount, ticketCount,
getEvent, getTicket, getEvents,
getUserTicketIds, getUserTicketCount, getSeatTicketIds, isChecker,
createEvent, setEventSalesPaused, setChecker,
buyTicket, checkIn, cancelEvent, refundTicket, withdrawProceeds.

НАСТРОЙКИ

Создай .env.example:
- VITE_CHAIN_ID
- VITE_RPC_URL
- VITE_CONTRACT_ADDRESS
- VITE_EXPLORER_URL

ABI хранить в src/contracts/TicketChain.abi.json.
Sepolia использовать как целевую тестовую сеть.
Проверять корректность адреса и наличие кода контракта в сети.
При ошибке конфигурации выводить понятное сообщение.
Секретные ключи и seed phrase не нужны и не должны запрашиваться.
VITE-переменные публичны: не помещать туда секреты.

АРХИТЕКТУРА

- readProvider для просмотра без подключенного кошелька;
- wallet provider и signer для транзакций;
- единый типизированный слой contractService;
- hooks для кошелька, мероприятий, мест, билетов;
- отдельный модуль загрузки metadata;
- общие компоненты состояний loading/error/empty;
- единый компонент статуса транзакции.

ETH/wei обрабатывать через parseEther/formatEther и bigint.
Не преобразовывать денежные значения в JS Number.
Учитывать секунды в контракте и миллисекунды в JavaScript.
При создании события явно показывать часовой пояс.
Для дат мероприятия использовать Asia/Qyzylorda с подписью UTC+5.

СТРАНИЦЫ

1. КАТАЛОГ /

- Шапка: логотип, афиша, мои билеты, переключатель языка, кошелек.
- Поиск по названию.
- Фильтры: город, категория, дата.
- Сортировка по дате и цене.
- Карточки: постер, название, дата, город, цена в тестовом ETH,
  оставшиеся места и статус.
- Отдельные состояния: загрузка, ничего не найдено, ошибка RPC.
- Избранное можно хранить в localStorage.
- Полноценная работа на мобильном экране.
- Фильтры должны работать по всему загруженному каталогу:
  последовательно получить все страницы событий с учетом
  размера учебного набора, не фильтровать лишь первую страницу.

2. МЕРОПРИЯТИЕ /events/:eventId

- Постер, название, описание, город, площадка, время начала/конца.
- Цена берется только из контракта.
- Схема нумерованных мест.
- Места: свободное, выбранное, проданное; различать не только цветом.
- Пользователь выбирает одно место.
- Сводка покупки: мероприятие, место, цена, отдельное пояснение gas.
- Купить можно только доступное место до начала мероприятия.
- Для отмененного/прошедшего события и остановленных продаж
  показывать соответствующий статус.
- Никакой фиктивной брони: выбор в браузере не резервирует место.
- Перед покупкой перечитать данные и выполнить предварительную
  проверку вызова; это не отменяет возможную гонку транзакций.
- Вызвать buyTicket(eventId, seatNumber) с точным value.
- Дождаться успешного receipt.
- Из TicketPurchased получить ticketId.
- Обновить места, счетчики, список билетов.
- Если место успели купить, показать понятное сообщение
  и предложить выбрать другое.
- Ссылка на транзакцию в explorer.

3. МОИ БИЛЕТЫ /my-tickets

- Без кошелька: приглашение подключить его.
- Получить билеты текущего адреса с пагинацией.
- Карточка: событие, место, ticketId, владелец, дата, статус.
- Статусы: действителен, использован, отменено — доступен возврат,
  возвращен, мероприятие завершено.
- Учитывать состояние и билета, и мероприятия.
- Открыть детальную карточку билета.
- Для отмененного события показать возврат через refundTicket.
- После receipt обновить данные.
- Печатная версия билета через browser print.
- QR-код без персональных данных.

4. БИЛЕТ /tickets/:ticketId

QR содержит JSON:
{
  "version": 1,
  "chainId": "<configured chain id>",
  "contractAddress": "<configured contract>",
  "ticketId": "<id as decimal string>"
}

QR — идентификатор, не секрет и не доказательство владения.
Показывать текущего владельца и актуальный статус из контракта.
Не скрывать публичность on-chain данных за фиктивной авторизацией.

5. АДМИН-ПАНЕЛЬ /admin

Доступные действия зависят от адреса admin/organizer,
прочитанного из контракта.
Реальное ограничение прав обеспечивается контрактом.

- Создание мероприятия:
  название, metadataURI, начало/конец, цена в ETH, вместимость 1..200.
- Предпросмотр metadata:
  description, city, venue, category, posterUrl.
- Валидация URI, дат, цены и вместимости.
- Таблица созданных событий.
- Статистика из контракта:
  продано, проверено, возвращено, escrowBalance.
- Остановка/возобновление продаж.
- Назначение/отзыв checker по адресу для каждого события.
- Отмена события с показом последствий и подтверждением.
- Вывод средств только после endsAt для неотмененного события.
- Не показывать активными действия, запрещенные текущим состоянием.
- Ошибки контракта все равно обрабатывать.

Для metadata реализуй:
- форму создания JSON;
- скачивание JSON;
- поле URL уже размещенного JSON;
- предварительную проверку загрузки.
Без backend или IPFS-сервиса не изображать загрузку файла
в интернет как выполненную.

6. ПРОВЕРКА /check-in

- Пользователь выбирает мероприятие.
- Проверить isChecker для подключенного адреса.
- QR-сканер с запросом разрешения камеры.
- Если камеры нет, доступ запрещен или нет HTTPS:
  ручной ввод ticketId и вставка QR JSON.
- Проверять version, chainId, contractAddress и корректность ticketId.
- Не открывать автоматически произвольные URL из QR.
- Проверять, что билет относится к выбранному мероприятию.
- Отобразить мероприятие, место, owner и актуальный статус.
- Предупредить проверяющего: QR можно скопировать.
- Перед пропуском проверяющий подтверждает, что сверил владельца
  отдельным способом; не заявлять криптографическую защиту
  от копирования QR в этой версии.
- Кнопка «Подтвердить вход» вызывает checkIn(ticketId).
- Зеленый результат «Вход подтвержден» только после успешного receipt.
- Повторный вход, чужое мероприятие, отмена, возврат, неправильное
  время и отсутствие прав показываются как разные ошибки.
- Останавливать камеру после ухода со страницы.

КОШЕЛЕК И ТРАНЗАКЦИИ

- Просмотр каталога без MetaMask через read-only RPC.
- При отсутствии MetaMask показывать инструкцию подключения.
- Connect Wallet только по действию пользователя.
- Обрабатывать accountsChanged и chainChanged.
- При смене адреса сбрасывать старые билеты, роли и запросы.
- При неверной сети предложить переключение.
- Не отправлять транзакции в неверную сеть.
- Не смешивать BrowserProvider с API ethers v5.
- Показывать стадии:
  ожидание подписи, отправлено, ожидание включения,
  подтверждено, отклонено/ошибка.
- Не считать tx hash подтверждением успеха.
- Обрабатывать отказ пользователя, нехватку средств на цену + gas,
  revert, RPC-сбой, замененную или отмененную транзакцию.
- Не давать повторно отправить одно действие, пока оно выполняется.
- После подтверждения обновлять данные.
- Обновлять занятость мест при возвращении на вкладку и периодически;
  очищать подписки и интервалы.
- Не стирать информацию об отправленной транзакции при смене аккаунта.

ДИЗАЙН

Создай современный билетный сервис:
- светлый основной фон;
- темный читаемый текст;
- один яркий акцентный цвет;
- крупные качественные постеры;
- понятная визуальная иерархия;
- аккуратная сетка и единые отступы;
- адаптация от 360 px до широкого desktop;
- видимые focus states, подписи полей, keyboard navigation;
- контрастные состояния и доступные диалоги;
- skeleton, empty, error и success states.

Не добавлять декоративные кнопки без действия.
Для отсутствующего постера использовать аккуратный fallback.
Не вставлять HTML из metadata через небезопасный innerHTML.
При ошибке metadata оставлять доступными on-chain данные
и основные действия.
В интерфейсе явно обозначить тестовую сеть и тестовый ETH.
Не показывать фиктивную оплату банковской картой или цену в тенге
как реальную сумму блокчейн-платежа.

ДЕМО-ДАННЫЕ

Подготовь 6 локальных metadata JSON и соответствующие постеры
либо легально доступные изображения с fallback.
Примеры: концерт, киносеанс, stand-up, спектакль,
университетское событие, киберспортивный турнир.

Это только metadata, а не существующие on-chain мероприятия.
Дай инструкцию размещения JSON и создания соответствующих
мероприятий через admin.
Даты вычислять относительно запуска.
Не показывать фиктивные билеты как реально купленные.
